### 4.196 Rust 全批量评估函数修复（2026-07-22，已完成）

**背景**：`evaluate_full_batch_py`（Tier 4 全批量路径）存在 4 个 bug 导致无法正确使用，搜索性能停滞在 ~30s/97万组合。

**修复的 4 个 Bug**：

| 严重度 | Bug | 修复 |
|:------:|-----|------|
| 🔴 HIGH | 装备目录结构不匹配 — Python 用 `accessories`（单列表），Rust 期望 `acc_a` + `acc_b` | `full_batch_eval.py` 自动将 `accessories` 拆为笛卡尔积 |
| 🔴 HIGH | 暴击模式硬编码 `let crit = 1.0` — 忽略 `crit_mode` | `full_batch.rs` 复用 `zones::crit_zone()` 支持三种模式 |
| 🟡 MED | 效果累加不完整 — 缺少 `失衡易伤系数` 等效果类型 | `full_batch.rs` 复用 `evaluate.rs` 的完整 14 种效果处理 |
| 🟡 MED | 抗性计算不一致 — 无 clamp 和穿透逻辑 | `full_batch.rs` 统一使用 `zones::resistance_zone` |

**新增参数**：`crit_mode`（"non_crit"/"always_crit"/"expected"）和 `damage_pipeline`（"normal"/"abnormal"）

**涉及文件**：

| 文件 | 改动 |
|------|------|
| `extensions/rust_search/src/full_batch.rs` | 重写评估逻辑，添加 crit_mode/damage_pipeline 支持 |
| `extensions/rust_search/src/lib.rs` | `evaluate_full_batch_py` 添加新参数（带默认值） |
| `extensions/rust_search/python/rust_bridge.py` | 包装函数添加新参数透传 |
| `games/endfield/calc/search/evaluate/full_batch_eval.py` | 修复装备目录格式 + 传递 crit_mode/damage_pipeline |
| `games/endfield/calc/search/evaluate/rust_batch_data.py` | `CalcParams` 添加新字段 |

### 4.197 Python 预处理优化 — 消除重复开销（2026-07-23，已完成）

**背景**：`_preprocess_for_rust_soa` 中每个任务都要构建 `DamageContext` + 调用 `_collect_effects` + 效果→u8 ID 映射，是搜索热路径的主要 Python 开销。

**优化方案**：3 层缓存

| 优化 | 机制 | 效果 |
|------|------|------|
| 作用域过滤器缓存 | `_SCOPE_FILTER_CACHE` — 同批次内 damage_type/skill_type/is_unbalanced 恒定，过滤器只构建 1 次 | 消除 999 次 DamageContext 构建 + _collect_effects 调用 |
| 效果 ID 缓存 | `_EFFECTS_ID_CACHE` — 相同效果列表直接返回缓存的 (ids, values) | 相同装备组合的任务跳过效果→ID 映射 |
| 破防效果缓存 | `_break_defense_cache` — 按层数缓存破防易伤效果 | 消除重复的 `damage_effects_from_break_defense` 调用 |

**新增函数**：`_build_scope_filter(ctx)` — 构建轻量级过滤闭包，内部按 effect_type 缓存过滤决策。

**涉及文件**：`extensions/rust_search/python/rust_bridge.py`

**测试结果**：搜索 206 passed ✅，全量 1606 passed ✅

**状态**：✅ 已完成（v3.29.10）

### 4.198 SoA 数据布局优化 — 内联 snapshot + 装备效果缓存（2026-07-23，已完成）

**背景**：`_build_batch_params` 每个任务调用 `build_runtime_eval_snapshot`（函数调用开销 + dict 构建 + tuple 拼接），是搜索循环的 Python 瓶颈。

**优化方案**：

| 优化 | 机制 | 效果 |
|------|------|------|
| 内联 snapshot 构建 | 将 `build_runtime_eval_snapshot` 核心逻辑直接写入 `_build_batch_params` | 消除每个任务的函数调用开销 |
| 装备效果缓存 | `equip_effects_cache`（跨批次复用） | 相同装备组合的 `aggregate_loadout_modifiers` 只调用一次 |
| 公共参数预计算 | 将 `base_context` 的 18 个字段提前提取为局部变量 | 避免每个任务重复属性访问 |

**涉及文件**：`games/endfield/calc/search/evaluate/task_batch.py`

**测试结果**：搜索 206 passed ✅，全量 1445 passed ✅

**状态**：✅ 已完成（v3.29.11）

### 4.199 act 代理修复 + CI 镜像源问题（2026-07-23，已完成）

**背景**：本地 act 运行 CI 测试时，`act` 自身（Go 二进制）clone GitHub actions 失败，因为 `--env HTTP_PROXY` 只影响容器内命令，不影响 `act` 自己的 git 操作。

**修复**：

| 问题 | 根因 | 修复 |
|------|------|------|
| act 无法 clone GitHub actions | `act` 进程自身没有 `HTTPS_PROXY` 环境变量 | `act.ps1` 自动设置 `$env:HTTPS_PROXY` 给 act 进程 |
| CI 镜像源 502 | 本地代理/网络临时问题，不是 Ubuntu 镜像问题 | 不需要修复 |

**关键发现**：
- 容器内 `host.docker.internal:6518` 可达（HTTP 200），但 `127.0.0.1:6518` 不可达
- `us.archive.ubuntu.com` 解析到 IPv6 且超时，**不能**用作替代镜像
- `archive.ubuntu.com` 是全球 CDN，GitHub runner 上不会出问题

**涉及文件**：`scripts/act.ps1`

**状态**：✅ 已完成（v3.29.10）
