## 2. 严重（Critical）— 逐项核实

### C1 · search.py 异常消息直接泄露 `[SEV-CRITICAL]`

| 项 | 内容 |
|----|------|
| **声称** | `search.py:154, 189, 210` 三处 `str(e)` 直接返回给客户端 |
| **核实** | ✅ **确认**。发现大于声称：`search.py:263` `f"批量评分失败: {e}"`、`:320` `f"预估失败: {e}"`、`:379` `f"搜索失败: {e}"`、`:437` `f"获取装备目录失败: {e}"`、`:527` `str(e)` |
| **根因** | `compute.py` 已使用 `raise_http_from_exc` 安全封装，但 `search.py` 未同步 |
| **状态** | ✅ **已修复**（`raise_http_from_exc` + 公共错误消息） |

### C2 · 全局无 CSRF 保护 `[SEV-CRITICAL]`

| 项 | 内容 |
|----|------|
| **声称** | `main.py:30-35` 使用 `allow_credentials=True` 且无 CSRF 中间件 |
| **核实** | ✅ **确认**。`main.py:44-50` CORSMiddleware 配置 `allow_credentials=True`，但**无任何 CSRF token 校验** |
| **影响** | 同源请求可被 CSRF 攻击利用 |
| **状态** | ✅ **已修复**（`CSRFSkipMiddleware` / Origin+Referer；WSGI 层另有补修） |

### C3 · DNS 重绑定（TOCTOU）SSRF 绕过 `[SEV-CRITICAL]`

| 项 | 内容 |
|----|------|
| **声称** | `safe_http.py:67-78` 验证时一次 DNS 解析，client 创建时再次解析，存在 TOCTOU 窗口 |
| **核实** | ✅ **确认**。`validate_outbound_api_base()`（`:48` `socket.getaddrinfo`）与 `post_chat_completions()`（`:115` 新 `httpx.AsyncClient`）各自独立 DNS 解析。 |
| **影响** | 攻击者可在两次解析间切换 DNS 响应，绕过 SSRF 防护 |
| **状态** | ✅ **已修复**（验证时钉扎 `resolved_ip`，请求走 IP） |

### C4 · 硬编码 dev pepper `[SEV-CRITICAL]`

| 项 | 内容 |
|----|------|
| **声称** | `admin.py:84-88` `CALC_API_KEY_PEPPER` 环境变量未设置时回退到硬编码 pepper |
| **核实** | ✅ **确认**。当时存在 `_DEV_PEPPER` 回退逻辑 |
| **影响** | 获取 `api_keys.json` 后可离线暴力破解 |
| **状态** | ✅ **已修复**（移除硬编码回退；缺环境变量即 `RuntimeError`） |

### C5 · 多 Worker 下速率限制完全失效 `[SEV-CRITICAL]`

| 项 | 内容 |
|----|------|
| **声称** | `admin.py:148-153` `_window: dict[str, list[float]]` 为进程内存，多 worker 各自独立计数 |
| **核实** | ✅ **确认**。进程内 `_window`；docstring 自述单 worker 限制 |
| **影响** | 攻击者可向不同 worker 分发请求完全绕过限速 |
| **状态** | ⚠️ **接受风险 / 文档化** — 推荐单 worker 部署；未实现 Redis 等共享计数 |
