## Web `/api/adapters/{目录id}/schema` 返回 404（2026-11-05，已修复）`[SEV-MED]`

**现象**：`GET /api/adapters/wjdlglr/schema` 返回 404；`AdaptersPage` 中目录 id 与显示名不一致的适配器无法展开 schema。

**根因**：`web/backend/api/adapters.py::get_schema` 直接用路径参数 `name` 调 `AdapterManager.load(name)`；而 `AdapterManager` 以 `meta.json` 的 `name` 显示名（如「无尽的拉格朗日 武器输出计算器」）为 key，目录名 `wjdlglr` 查不到。

**修复**：先 `_validate_adapter_id()` 校验路径，再 `load_adapter_meta(adapter_id)` 读取 meta，用 `meta["name"] or adapter_id` 调 `load()`；加载失败映射为 404。

**回归测试**：`web/backend/tests/test_api_integration.py::test_wjdlglr_schema_endpoint`（200，45 个属性含 `hit_rate_bonus` / `base_damage`）；`test_adapter_schema_endpoint` 收紧为非空断言。

**涉及文件**：`web/backend/api/adapters.py`、`web/backend/tests/test_api_integration.py`

## Qt 数字输入框默认上限 99.99 / 99，无上限输入被静默截断（2026-11-05，已修复）`[SEV-MED]`

**现象**：查看器输入「编组数量」最大只能填 99，伤害加成、护甲等小数输入最大只能填 99.99；超出部分无法键入，界面没有报错，用户误以为公式只支持小数值。

**根因**：`sheet_widgets.make_spinbox` 创建 `QDoubleSpinBox` / `QSpinBox` 后未设置上限时，会沿用 Qt 默认的 `99.99` / `99`；`ControlSpec` 只在 DAG 显式声明 `max` 时才调用 `setMaximum`，因此「未声明上限」被误解为「使用 Qt 默认上限」。

**修复**：`framework/src/calc_framework/ui/sheet_widgets.py` 增加 `_NO_MAX_INT = 2_147_483_647`、`_NO_MAX_FLOAT = 1_000_000_000_000.0`；未声明 `max` 时按控件类型设置上述哨兵上限，显式 `min` / `max` 仍优先，并应用 `ui_control.suffix`（如 `%`）与步长。

**回归测试**：`framework/tests/ui/test_spinbox_limits.py` — float/int 无默认上限、显式 max 生效、`ui_control` 推断 suffix/step、suffix 实际应用。

**涉及文件**：`framework/src/calc_framework/ui/sheet_widgets.py`、`framework/src/calc_framework/ui/controls.py`、`framework/tests/ui/test_spinbox_limits.py`

## i18n 占位符使用单花括号，界面直接显示 `{n}`（2026-11-03，已修复）`[SEV-MED]`

**现象**：Web 界面多处显示原始占位符，例如 DAG 编辑器节点计数显示 `{n} 个节点`、搜索预估显示 `{combinations}`、配置包市场显示 `共 {n} 个配置包`。Cypress `editor-page.cy.ts` 的「清空按钮重置画布」因此失败。

**根因**：`web/frontend/src/i18n/locales/{zh-CN,en}.ts` 中有 72 处/语言使用 `{name}` 单花括号，而 i18next 默认插值语法是 `{{name}}`。`config.ts` 未修改插值前后缀，因此这些占位符从不被替换。

**修复**：将两个 locale 文件中所有 `{identifier}` 占位符统一改为 `{{identifier}}`（已有 `{{count}}` 保持不变）。

**验证**：`npx tsc -b`、`eslint`、`vitest run`（49 passed）通过；DAG 空画布计数渲染为 `0 个节点`，Cypress 用例通过（见 §4.246）。

**涉及文件**：`web/frontend/src/i18n/locales/zh-CN.ts`、`web/frontend/src/i18n/locales/en.ts`

## `usage.json` 并发读改写导致文件损坏，所有 API 请求返回 500（2026-11-03，已修复）`[SEV-HIGH]`

**现象**：Web E2E 运行中 `/api/arknights/operators` 等接口随机返回 500，后端日志为 `JSONDecodeError: Extra data`；`web/backend/.data/admin/usage.json` 内容形如 `{"request_timestamps": [], "by_endpoint": {}}}\n}`（尾部半截 JSON）。

**根因**：`RateLimitMiddleware._record_usage_async` 由每个请求触发，先读文件、再修改、再整体写回，且通过多个 `to_thread` 并发执行；没有锁，两个请求交错写会互相覆盖，写入非原子还会让读者读到写了一半的内容。损坏后的文件在下一次读取时抛 `JSONDecodeError`，限流中间件对**所有**请求返回 500。

**修复**：
- 新增模块级 `_USAGE_WRITE_LOCK = threading.Lock()`，把整段「读-改-写」收敛到 `_record_usage_sync`，由锁串行化；`_record_usage_async` 只负责 `asyncio.to_thread`。
- `_save_json` 先写 `*.tmp` 再 `Path.replace` 原子替换，读者不会看到半截文件。
- `_load_json` 捕获 `(json.JSONDecodeError, OSError, UnicodeDecodeError)` 并返回 `{}`，统计文件损坏不再拖垮业务接口。

**回归测试**：`web/backend/tests/test_admin_usage_persistence.py` — 损坏文件返回 `{}`；20 个并发 `_record_usage_async` 后 `by_endpoint["/api/x"] == 20`（修复前为 1）。

**涉及文件**：`web/backend/api/admin.py`、`web/backend/tests/test_admin_usage_persistence.py`

## Web E2E 在 act 容器内无法运行 + 用例断言漂移（2026-11-03，已修复）`[SEV-MED]`

**现象**：`act` 执行 `web-e2e.yml` 时 Cypress 无法启动；能启动后又出现大面积失败：约 40 个用例失败、页面渲染英文、后端日志刷 429。

**根因与修复**：

| 问题 | 根因 | 修复 |
|------|------|------|
| Cypress 启动失败 | act 镜像缺 `xvfb`/`libgtk`/`libnss3` 等运行库；无 X server | 容器内安装 Cypress 运行依赖并常驻 `Xvfb :100`，运行时注入 `DISPLAY=:100` |
| Cypress 二进制下载慢 | `download.cypress.io` 约 140 KB/s（247 MB） | 通过 `CYPRESS_INSTALL_BINARY` 指向 npmmirror 镜像（约 2.7 MB/s） |
| 界面渲染英文 | Electron 不支持 `before:browser:launch` 的 `--lang=zh-CN`（Cypress 警告并忽略） | `i18n/config.ts` 的检测顺序改为 `localStorage → navigator → htmlTag`；Cypress support 在 `window:before:load` 写入 `i18nextLng=zh-CN` |
| 接口 429 | 匿名限流 20 次/分钟，E2E 单页十余个请求 | workflow 启动后端时设置 `CALC_DISABLE_RATE_LIMIT=1`（限流属部署层） |
| 用例断言过期 | 断言英文文案（`START CALCULATING`）、不存在的标题（`角色选择`）或已改版控件（`MuiAutocomplete`、布局页 DAG 编辑器） | 按现行 UI 更新断言：`角色 / 武器选择`、`明日方舟 伤害计算器`、`敌军防御力`、`公式图编辑器`、`多技能次数` 等 |

**验证**：见 `docs/会话接续手册.md` §4.246 ④（act/Docker 实际执行结果：11 spec / 76 用例全部通过，33s）。

**补充（第二轮 70/76 → 76/76）**：首轮剩余 6 个失败均为断言与真实 UI 不一致——
- AI 推荐按钮实际渲染 `ai.recommend`（`AI 推荐`），组件中的 `"AI 智能推荐"` 只是 i18n 缺失时的兜底；
- 等级滑块位于页面顶部，被固定 AppBar（`MuiToolbar`）遮挡，`cy.trigger()` 拒绝执行，需 `{ force: true }`；
- 敌人面板法抗输入标签是 `arknights.magicResistance`（`法术抗性`），`敌军法抗` 只出现在计算后的结果表。

**涉及文件**：`.github/workflows/web-e2e.yml`、`web/frontend/src/i18n/config.ts`、`web/frontend/cypress/support/e2e.ts`、`web/frontend/cypress/support/helpers.ts`、`web/frontend/cypress/e2e/*.cy.ts`、`web/frontend/src/components/calculator/CharacterSelector.tsx`、`web/frontend/src/components/arknights/OperatorSelector.tsx`

## NSIS 构建因 UTF-8 脚本按 ACP 读取而失败（2026-11-03，已修复）`[SEV-MED]`

**现象**：本机（中文 Windows）执行 `python installer/build_installer.py` 报 `Bad text encoding: ...\.nsi:1`，安装包构建中止。CI（en_US）即使不报错，也会把中文文案读成乱码。

**根因**：`installer/endfield_calculator_setup.nsi` 为 UTF-8 无 BOM（项目规范），而 `makensis` 默认按系统 ACP（GBK/CP1252）读取脚本；`Unicode True` 只影响输出，不改变源文件解码。

**修复**：`installer/build_installer.py` 的 makensis 命令增加 `-INPUTCHARSET UTF8`；新增回归测试 `test_build_installer_passes_utf8_input_charset`（`tools/tests/test_installer_layout.py`）。

**验证**：7 项安装器测试通过；本机成功产出 `dist/GameCalcPlatform_Setup_v0.7.0-beta.exe`（383.3 MB）；用户级同构安装包完成「安装 → 启动（窗口标题正常）→ 卸载」闭环，文件、注册表、快捷方式、`.calcpack` 关联均正确清理。提权（HKLM / Program Files）流程因非交互会话无法通过 UAC，未实机执行。

**涉及文件**：`installer/build_installer.py`、`tools/tests/test_installer_layout.py`

## 全批量搜索逐组合重算最终攻击力导致 28s（2026-11-03，已优化）`[SEV-MED]`

**现象**：固定 973,728 组合基准中，`rust_full` 耗时 28.36s，远超 `<10s` 目标；`rust_soa` / 纯 Python 更慢。

**根因**：`_precompute_final_attacks_for_batch` 对每个组合调用一次完整乘区链（`final_attack_details_for_loadout`），并在每次调用中重复解析武器技能选用状态、复制角色/武器字典。但最终攻击力只依赖装备的 `攻击力`、角色主/副能力值、`攻击力%` 四个数；973,728 个组合中只有约 **56,454** 个唯一签名（约 5.8%），其余都是重复计算。

**修复**：
- 按 `(攻击力, 主能力, 副能力, 攻击力%)` 记忆化最终攻击力；缓存按武器分隔，避免跨武器复用结果。
- 武器技能选用状态每把武器只解析一次，通过 `skill_calculation_kwargs` 传入。

**回归测试**（`games/endfield/tests/calculation/search/evaluate/test_full_batch_precompute.py`）：
- 重复签名只计算一次（2 武器 × 3 组合 → 4 次调用）。
- 缓存值与逐组合直接计算逐值一致。
- 相同装备属性在不同武器下结果不同。
- 缺武器数据时返回 `None` 回退 SoA。

**验证**：`rust_full` 28.36s → **9.75s**（99,878 组合/s，峰值 634 MB），`<10s` 达成；TopN 三模式一致；取消/续跑仍通过；既有 6 条全批量 parity 测试通过。

**涉及文件**：`games/endfield/calc/search/evaluate/full_batch_eval.py`、`games/endfield/tests/calculation/search/evaluate/test_full_batch_precompute.py`

## Rust 全批量忽略效果作用域导致伤害偏高（2026-11-03，已修复）`[SEV-HIGH]`

**现象**：P3-01 性能基准发现 `rust_full` 与 `rust_soa` / 纯 Python 的 TopN 不一致，全批量结果整体偏高。缩小到单配装复现：同一把武器、同一套装备，`rust_full` 最终伤害 **11096.62**，直接调用 `evaluate_task` 为 **10007.43**；差值正好等于把一条 `skill_types=('终结技',)` 的 `技能类型伤害加成 0.431` 计入了**战技**搜索。

**根因**：
1. `full_batch_eval.evaluate_full_batch_rust()` 为适配 Rust 接口，把武器/装备效果压平成 `(effect_type, value)` 列表，丢弃了 `DamageEffect` 的 `damage_types` / `skill_types` / `require_unbalanced`。Rust 侧只看到类型和数值，无法再按当前搜索上下文过滤，作用域外的效果被无条件应用。
2. `extensions/rust_search/python/rust_bridge.py::_build_scope_filter` 的缓存键只有 `effect_type`。同一效果类型若同时存在不同作用域（例如两组 `技能类型伤害加成`，一组限终结技、一组不限），后一个会复用前一个的 `_match_scope` 结果，造成漏过滤或误过滤。

**修复**：
- 新增 `full_batch_eval._scope_effect_filter(base_context)`：用 `KNOWN_EFFECT_TYPES` + `_match_scope` 逐效果判断，缓存键为 `(effect_type, damage_types, skill_types, require_unbalanced)`；武器效果与装备聚合效果在送入 Rust 前都先过滤。

## 武器同步「全部条目误报为需更新」（2026-09-29，已定位，未修复）`[SEV-MED]`

**问题**：`python -m tools.bwiki_scout --apply --new --full` 每次都报告「62 条武器更新」，但写入后 `weapons.json` 与写入前**语义完全相同**（逐条 deep-equal 相等）。干员路径无此现象。

**现象**：

| 路径 | 报告 | 实际 |
|------|------|------|
| 干员 | `计划 0 条` | 与 Wiki 一致 ✅ |
| 武器 | `计划 62 条（更新 62）` | 零变化 ❌ 误报 |
| 装备 | 163 条重写 | 零变化（无「需更新」判定，直接重写） |

**根因**：`tools/bwiki_scout/weapon_wiki.py:needs_weapon_sync_with_wiki()` 按**旧 schema** 读取本地记录：

| 函数读取的字段 | 迁移后 `weapons.json` 的实际位置 |
|---------------|------------------------------|
| `local_record["基础攻击力"]`（等级数组） | `成长参数.基础攻击力`（参数 dict） |
| `local_record["主能力值+"]` 等顶层词条键 | `normal_skills[].effect` / `special_skills[].effect` |

两条路径均命中 `if not isinstance(local_arr, list): return True`，函数**必然返回 `True`**，故每把武器每次都被判为「需更新」。

**为何干员路径正确**：`characters.json` 保存的是**烘焙等级数组**（`力量` / `战技倍率` 等均为数组），与 `needs_sync_with_wiki()` 的期望一致。

**影响**：
1. 每次同步都重算并重写全部武器（实测约 6 分钟）
2. `--bump-version` 因 `updated_count > 0` 误判「有数值变化」→ 无变更也 bump PATCH
3. **真实数值变更无法从报告辨识**（永远显示「全部更新」）

**写入路径不受影响**：`add_weapon()` 照常写入正确数据，数据本身不会出错。

**建议修复**：`needs_weapon_sync_with_wiki()` 增加新 schema 分支——优先读 `成长参数` + `normal_skills` / `special_skills`，读不到再回退旧字段；或与已支持新 schema 的 `read_weapon_special_slots()`（`games/endfield/calc/skills/special_fields.py`）对齐。

**规避**：判断武器是否真有变化，用 `git diff` 或语义 deep-equal，**不要**相信「计划 N 条」。

**涉及文件**：`tools/bwiki_scout/weapon_wiki.py`、`tools/bwiki_scout/wiki_sync.py`、`tools/bwiki_scout/bump_data_version.py`

**状态**：🔴 已定位，未修复（2026-09-29 核查中数据零变化，未产生实际影响）

## 桌面 GUI / 打包 exe 部分

### PyInstaller exe 全量遍历崩溃

**问题**：打包后的 `Game Calc Platform.exe` 启动全量装备遍历时进程闪退或无响应；开发模式 `python games/endfield/main.py` 正常。

**原因**：
1. 全量搜索默认 `parallel_backend=auto`，`max_workers>1` 时使用 `ProcessPoolExecutor`
2. Windows + PyInstaller onefile：`spawn` 会反复启动整个 exe 解压包，与 PySide6 / Rust `rust_search.pyd` 冲突，易 segfault
3. 批量路径曾误在 `parallel_backend=thread` 时仍走多进程；续跑 `(key, task)` 元组未剥离就送入进程 batch worker，异常被 `_run_parallel_loop` 吞掉导致 `processed=0`

**修复**（2026-06-16）：
1. `parallel.py`：`sys.frozen` 时强制 `thread` 后端（单进程线程池 + Rust 批量，不再 spawn 子 exe）
2. `parallel.py`：批量路径按已解析的 `backend` 选线程/进程，不再仅因 `process_payload` 存在就 ProcessPool
3. `process_worker.py`：新增 `evaluate_optimizer_batch_keyed_in_process` 剥离 combo key
4. `persist/store.py`：续跑仅在 `total_combinations > batch_size` 时启用批量
5. `launcher_entry.py` / `games/endfield/main.py`：`multiprocessing.freeze_support()` 提前到 `__main__` / `main()` 入口
6. `main_build.py`：`hidden-import rust_search` + `collect-submodules extensions.rust_search`
7. `utils/search_diagnostics.py`：统一写入 exe 旁 `logs/`（`search.log` / `crash.log` / `app.log`），GUI 搜索线程与并行循环记录进度与异常

**续查修复**（2026-06-16，崩溃仍发生时）：
1. `persist/store.py` / `in_memory_optimizer.py`：GUI 传入 `search_job` 时改用 `make_loadout_task_evaluator`，**不再**对续跑项误走 `evaluate_task_batch`
2. `parallel.py`：`sys.frozen` 时 `_resolve_max_workers()` 强制为 **1**
3. `optimizer/evaluate.py`：`_loadout_cache` 加 `threading.Lock`
4. `rust_bridge.py`：Rust FFI 调用加全局锁

**深层修复**（2026-06-16，仍崩溃）：
1. **Qt 跨线程信号**：`SearchWorker` 在 QThread，但 `ThreadPoolExecutor` 回调里 `progress.emit()` → PySide6 随机崩溃；`sys.frozen` 时改 `_run_inline_loop` 在调用线程顺序执行（`executor=inline`）
2. **PyInstaller + rust_search.pyd**：frozen 启动时默认 `RUST_SEARCH_FALLBACK=1`（`launcher_entry.py` / `games/endfield/main.py`，须在 `rust_bridge` 导入前）
3. `endfield_search.py`：搜索信号显式 `QueuedConnection`

**第四轮**（仍崩溃 — 最激进路径）：
1. **`endfield_search.py`**：frozen 下**不用 QThread**，主线程同步跑 `SearchWorker.run()` + `processEvents()` 泵进度（彻底消除 Qt 跨线程）
2. **`utils/frozen_runtime.py`**：frozen 恒 `use_rust_search_accel()=False`；`evaluate.py` **不再 import rust_bridge**
3. **`spawn_detached`**：子进程继承 `RUST_SEARCH_FALLBACK=1`

## 合并分支与 CRLF 处理（2026-06-19）

**问题**：`--minor` 上传后合并 develop → main 时，`.gitattributes` 要求 Python 文件使用 LF 但本地为 CRLF，git 一直将文件视为"已修改"，导致 `git checkout` 和 `git merge` 反复失败。

**根因**：
- `.gitattributes`：`* text=auto` + `*.py text eol=lf`
- Windows 上 `core.autocrlf=true` 导致检出时自动转为 CRLF，与 `.gitattributes` 冲突
- `git stash` 后 CRLF filter 立即重新修改文件，使 stash 失效

**修复**：
- 上传脚本 `_merge_work_into_release()`：`checkout` 到 main 后先执行 `git add --renormalize` + `git checkout -- .` 归一化换行符
- 全局关闭 `core.autocrlf=false`

**涉及文件**：`scripts/tools/github_upload_module.py`

## 子图 user_input 参数未提升为顶层变量（2026-06-29）

**问题**：图编辑器中复合节点（子图）内的 `user_input` 节点编译后只存在于子图 `parameters` 中，不生成顶层 `variables`。导致布局编辑器变量列表为空，ComputeSheet 无法渲染输入控件。

**根因**：编译器（`compiler.py`）和适配器加载器（`adapter.py`）只处理顶层 `variables`，未遍历子图 `parameters`。而 `user_input` 节点在子图内，其信息被困在 `subgraph.parameters` 中。

**修复**：
- `compiler.py`：编译复合节点时，检查 `dag_n.bindings`，只提升未连线的 `user_input` 参数
- `adapter.py`：`_promote_subgraph_user_inputs()` 递归收集所有 CallNode 绑定，只提升 `bindings[param_id] == ""` 的参数
- 变量路径格式：`子图名.节点标签`（如 `模拟计算.输入1`）

**关键约束**：只有未连线的 `user_input` 才提升——已连线的参数由上游节点提供值，不需要用户输入。

**涉及文件**：`framework/src/calc_framework/graph_editor/compiler.py`、`framework/src/calc_framework/config/adapter.py`
