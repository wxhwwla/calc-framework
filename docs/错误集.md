## github_upload_module.py 分支切换失败

**问题**：在 main 分支运行上传脚本时，`git checkout develop` 失败后尝试 `git checkout -b develop`，因 develop 已存在本地而报错退出。

**原因**：
1. 原始代码在 `git checkout develop` 失败后，无条件执行 `git checkout -b develop main` 和 `git checkout -b develop`
2. 当 develop 已存在但 checkout 因本地改动失败时，`-b` 标志与已存在分支冲突

**修复**（v3.24.1）：
1. `setup_git_repo()`: 在 `-b` 前检查 `git branch` 输出，若 develop 已存在则给出清晰错误提示并退出
2. `_merge_work_into_release()`: 同样模式——main 已存在但 checkout 失败时取消合并而非尝试 `-b`

**涉及文件**：
- `scripts/tools/github_upload_module.py` — `setup_git_repo()` 和 `_merge_work_into_release()`

**检查清单**：
- [x] 在 develop 分支运行上传脚本 → 正常工作
- [x] 在 main 分支有未提交改动时运行 → 提示手动处理
- [x] minor 上传后自动合并 main → 正常工作

## pre-commit mixed-line-ending hook 导致文件回退

**问题**：上传脚本运行 pre-commit 时，`mixed-line-ending` hook 修复了 CRLF，但脚本 abort 后未 `git add` 修复后的文件。下次运行 `git checkout` 时这些文件的修改丢失或冲突。

**原因**：pre-commit hook 修改文件后，若脚本在 `git add` 前 abort（如 checkout 失败），文件内容处于「被 hook 修改但未暂存」状态。后续 git 操作可能覆盖这些修改。

**修复**：修复 checkout bug（见上条）后，脚本能正常完成 `git add` 流程，hook 修改后的文件能正确暂存。

**涉及文件**：
- `.pre-commit-config.yaml` — `mixed-line-ending` hook

**检查清单**：
- [x] pre-commit 第 1 轮自动修正后，脚本正确 re-add 并重试
- [x] 第 2 轮通过后正常提交

## 新文件（untracked）在 git stash pop 时冲突

**问题**：`git stash --include-untracked` + `git checkout` + `git stash pop` 时，若目标分支已有同名文件，pop 会报 "already exists, no checkout" 并失败。

**原因**：`git stash --include-untracked` 保存了未跟踪文件，但切换到已有这些文件的分支时无法恢复。

**修复**：此方案已放弃。上传脚本改为仅在 develop 上运行，不做自动分支切换。如需跨分支，用户手动 `git stash && git checkout develop && git stash pop`。

**涉及文件**：
- `scripts/tools/github_upload_module.py`

**检查清单**：
- [x] 在 develop 分支直接运行上传 → 无此问题
- [x] 用户手动跨分支时，develop 上 stash pop 不应有冲突（文件内容一致）

## Web 前端部分

### WSGI `_handle_layout_compute` 缺少路径前缀守卫

**问题**：上传 `.calcpack` 到 Calc Hub（`POST /api/hub/packs/{id}/upload`，multipart/form-data）时返回 HTTP 400 `"invalid JSON"`。

**原因**：`wsgi_pythonanywhere.py` 中 `_handle_layout_compute` 函数对所有 POST 请求都尝试 `json.loads()` 解析 body。由于它在 handler 链中排在 `_handle_hub` 之前，multipart 上传数据被当成 JSON 解析失败，返回 400。`_handle_hub` 永远跑不到。

**修复**：在 `_handle_layout_compute` 开头加了路径前缀守卫：
```python
if not (path.startswith("/api/layout") or path.startswith("/api/compute")):
    return None
```

**涉及文件**：
- `web/wsgi_pythonanywhere.py` — `_handle_layout_compute()`

**检查清单**：
- [x] Hub 上传 multipart 正常
- [x] 不影响已有 layout/compute POST 请求

### `SurvivalEstimateDialog.tsx` 变量名遮蔽

**问题**：`tsc` 报错 `This expression is not callable`，`t` 同时作为 `useTranslation()` 返回的翻译函数和 `.map((t) => ...)` 的迭代变量。

**原因**：在 `.map((t) => ...)` 中，迭代变量 `t` 遮蔽了外层 `const { t } = useTranslation()`，导致 `t(TIER_I18N_MAP[t])` 中的外层 `t` 不再是函数。

**修复**：将 `.map((t) => ...)` 改为 `.map((tier) => ...)`：
```tsx
{ENEMY_TIERS.map((tier) => (
  <MenuItem key={tier} value={tier}>
    {TIER_I18N_MAP[tier] ? t(TIER_I18N_MAP[tier]) : tier}
  </MenuItem>
))}
```

**涉及文件**：
- `web/frontend/src/components/calculator/SurvivalEstimateDialog.tsx`

**检查清单**：
- [x] tsc --noEmit 零错误
- [x] 下拉框显示正常工作

## 桌面 GUI 部分

### i18n Agent 遗漏变量赋值导致 `NameError`

**问题**：运行 graph_editor 测试时报 `NameError: name 'tab' is not defined`。

**原因**：桌面 GUI i18n Agent 在重构 `node_panel.py` 的 `_build_tabs()` 时，移除了 `tab = DraggableTypeList(items, self)` 行，但保留了 `self.addTab(tab, tab_label)`，导致 `tab` 未定义。

**修复**：恢复 `tab = DraggableTypeList(items, self)` 行：
```python
tab = DraggableTypeList(items, self)
_tab_key_map = {...}
tab_label = tr(_tab_key_map.get(cat_name, ...))
self.addTab(tab, tab_label)
```

**涉及文件**：
- `framework/src/calc_framework/graph_editor/node_panel.py` — `_build_tabs()`

**检查清单**：

### JSON 文件中使用 Python 风格 `\U` Unicode 转义

**问题**：桌面 i18n 模块初始化时报 `json.decoder.JSONDecodeError: Invalid \escape`。

**原因**：i18n Agent 在生成 `en.json` 时使用了 Python 的 `\U0001f4e6`（📦）和 `\U0001f527`（🔧）格式。JSON 标准只支持 `\uXXXX`（4 位），不支持 `\UXXXXXXXX`（8 位）。

**修复**：将 `\U` 转义替换为原始 emoji 字符：
```json
"config": "\U0001f4e6 Config"  →  "config": "📦 Config"
"development": "\U0001f527 Development"  →  "development": "🔧 Development"
```

**涉及文件**：
- `framework/src/calc_framework/ui/i18n_data/en.json`
- `framework/src/calc_framework/ui/i18n_data/zh-CN.json`

**检查清单**：
- [x] `json.loads()` 通过
- [x] 桌面 i18n 模块 `tr()` 正常工作

## 部署部分

### PA 部署脚本重载前置导致站点挂掉

**问题**：部署中途 WSGI reload 失败（`slow_startup_error` 409），后续所有上传返回 500/502，站点不可用。

**原因**：优化部署流程时，将 `_reload_webapp()` 和 `_upload_wsgi()` 移到了 `_upload_dist_files()` 之前（为了让 dist zip 解压 API 可用）。但 PA 免费版 reload 可能因冷启动超时失败，一旦失败整个部署链断裂。

**修复**：恢复原始顺序 — 全部上传完成后再 reload：
1. 上传全部文件（包括 WSGI）
2. 最后一次性 reload
3. 不依赖 WSGI 端点在部署中途工作

**涉及文件**：
- `web/scripts/deploy_pythonanywhere.py` — Phase 3/4 顺序

**检查清单**：
- [x] 部署流程不会因 WSGI 中途挂掉而中断
- [x] reload 失败不影响文件已上传的事实
- [x] 用户可手动 reload 恢复站点

### PA Files API 冷启动导致并发上传首批全超时

**问题**：49 个 dist 文件 5 并发上传时，首批 5 个全部超时（30s），后续文件才逐渐正常。

**原因**：PA 免费版 Files API 有冷启动延迟，第一个请求极慢（>30s）。5 并发同时撞上冷启动，全部超时。

**修复**：并发上传前先发一个预热请求：
1. 单独上传 `index.html`（975 bytes），用较长的重试（max_retries=5, timeout=60s）
2. 预热成功后剩余 48 个文件再 5 并发上传

**涉及文件**：
- `web/scripts/deploy_pythonanywhere.py` — `_upload_dist_files()`

**检查清单**：
- [x] 预热请求单独通过，PA API 被激活
- [x] 后续并发上传不再集体超时

### `data_profiles.py` 数据文件不存在时抛 404

**问题**：PA 错误日志大量 `HTTPException: 404: 数据文件不存在: operators.json`。

**原因**：`_load_entity_list()` 在数据文件不存在时 `raise HTTPException(status_code=404)`。PA 上 `tools/arknights_scout/output/parsed/operators.json` 需要手动解压 zip 后才存在，但每次有人访问 profiles API 就会触发错误日志。

**修复**：文件不存在时返回空列表而非抛异常：
```python
if not ent.path.is_file():
    return []  # 数据文件尚未部署，返回空列表
```

**涉及文件**：
- `web/backend/api/data_profiles.py` — `_load_entity_list()`

**检查清单**：
- [x] 无 `operators.json` 时返回 `[]`，不记账错误
