# ADR-0010：全品类通用游戏战斗数值仿真框架路线图

**状态**：草案  
**日期**：2026-05-28  
**决策者**：维护者  
**影响范围**：`framework/` 全目录、`endfield_damage_calculator/`、`tools/designer/`

---

## 1. 现状定位

当前 calc-framework 是一套**二次元手游专用框架**：

| 维度 | 现状 |
|------|------|
| 数据模型 | 固定字段（攻击力、暴击率、能力值等终末地字段） |
| 公式结构 | 15 乘区链（二游模型） |
| 适用范围 | 仅二次元手游 |
| 受众 | 二游硬核玩家 |

---

## 2. 目标定位

将 calc-framework 从「二游专用工具」升级为**全品类通用游戏战斗数值仿真框架**。

### 旧定位 vs 新定位

| 维度 | 旧 | 新 |
|------|----|----|
| 受众 | C 端二游玩家 | C 端全体玩家 + **B 端游戏从业者** |
| 品类 | 仅二次元手游 | 端游/手游/单机/网游/MOBA/FPS/回合制/战棋 |
| 内核 | 二游规则强耦合 | 纯数学引擎 + 动态规则配置 |
| 价值 | 玩家提效工具 | 可复用的轻量化开源框架 |
| 开源许可 | GPL | GPL（个人/非商用）+ **商业双授权** |

### B 端新增受众（高价值增量）

- **独立游戏开发者**：用框架快速搭建战斗数值系统
- **游戏数值策划**：离线模拟配装、测算数值平衡、验算倍率
- **游戏工作室 / 模组作者**：私服验算、自制模组数值工具
- **攻略教学团队**：全品类攻略数据测算

## 3. 底层原理：所有游戏战斗数值的共通数学

市面上 95% 的电子游戏，战斗伤害逻辑都逃不出两套基础组合：

### 基础属性层
力量、攻击、法术、防御、血量、暴击、命中、闪避、攻速……
所有游戏都有，只是命名不同。

### 伤害运算层

```
基础伤害 = 面板攻击 × 技能倍率
叠加：加法乘区 / 乘法乘区 / 减伤区 / 易伤区 / 暴击区 / 护盾 / 格挡 / 免伤
附加：持续伤害、异常状态、Buff/Debuff、元素克制、护甲穿透
```

当前框架的 DAG 引擎 + AST 表达式沙箱已经能表达这套通用模型。把「游戏专属规则」全部抽离为可配置规则 + 动态表达式，内核就变为纯通用数学引擎。

## 4. 目标架构：五层完全解耦

```
┌─────────────────────────────────────────────────┐
│  层 5 │ 表现层（UI / Web / 桌面）                │
│       │ 配置驱动动态渲染、多主题、OCAR集成         │
├─────────────────────────────────────────────────┤
│  层 4 │ 游戏适配器层（轻量化）                    │
│       │ 每游戏一个适配包：数据转换 + 规则配置       │
│       │ 体量 几十~几百行，不动内核                │
├─────────────────────────────────────────────────┤
│  层 3 │ 通用数据模型层                            │
│       │ 动态字段键值对 {key, value}               │
│       │ 不固定任何游戏专属字段名                   │
├─────────────────────────────────────────────────┤
│  层 2 │ 通用战斗规则引擎（核心改造）                │
│       │ 动态表达式引擎 + 可插拔模块                │
│       │ 暴击/命中/护盾/衰减/元素 按需加载           │
├─────────────────────────────────────────────────┤
│  层 1 │ 纯数学计算内核（绝对通用）                  │
│       │ 四则运算 / 百分比 / 区间 / 概率 / 循环    │
│       │ 完全不知道"角色/装备/技能"是什么            │
└─────────────────────────────────────────────────┘
```

### 各层职责

| 层级 | 职责 | 是否需要改代码 |
|------|------|--------------|
| 1 纯数学内核 | 四则运算、百分比、区间、概率、循环 | 永久不用改 |
| 2 战斗规则引擎 | 动态表达式、模块插拔、乘区顺序配置化 | 通过配置，不改代码 |
| 3 通用数据模型 | 键值对属性、动态 schema | 通过配置，不改代码 |
| 4 游戏适配器 | 游戏数据 → 标准数据转换 | 每游戏写一个适配器 |
| 5 表现层 | 配置驱动动态 UI、主题 | 通过配置，不改代码 |

## 6. 关键改造项

### 6.1 表达式引擎增强（层2核心）

当前 DAG 引擎已支持 `expr` 节点和 AST 沙箱。增强方向：

- 开放自定义函数注册（`register_function()` — 本日已完成）
- 表达式字符串完整支持浮点/条件/函数组合
- 运行时热加载表达式（编辑 DAG JSON 即生效）

### 6.2 通用数据模型（层3）

当前：
```python
# 硬编码二游字段
character.基础攻击, character.暴击率, weapon.攻击力+
```

改造后：
```python
# 通用键值对
attrs["力量"] = 100
attrs["attack_power"] = 50
# 属性名由游戏适配器定义，内核只做数学运算
```

### 6.3 规则模块插件化（层2）

设计插件注册机制，按游戏品类按需加载：

```json
{
  "plugins": ["crit", "dodge", "shield", "distance_decay"],
  "formula": "clamp(base_damage * skill_mult, 0, cap) * crit_factor * distance_factor"
}
```

### 6.4 UI 动态渲染（层5）

- ComputeSheet 已支持配置驱动渲染
- 属性字段由适配器返回的 schema 动态生成
- 不同游戏只切换布局模板、文案、图标

## 9. 落地节奏

### 阶段 1：基础抽象（当前，已完成核心骨架）

- 公式/乘区全部可配置（DAG JSON）
- 自定义函数注册（`register_function()`）
- 日志系统（`calc_framework/logging.py`）
- 框架文档（`framework/README.md`, `docs/quickstart.md`）

### 阶段 2：跨品类验证（1 个月内）

- 新增 2~3 款不同类型游戏适配器
  - 一款武侠网游（攻击-防御公式）
  - 一款卡牌手游（简单倍率公式）
- 验证：只写适配器 + 配置，不动内核即可正常运行
- 目标：证明框架真正跨品类可用

### 阶段 3：模块扩展（1~2 个月）

- 插件模块：护盾、衰减、暴击时序、距离衰减
- 适配 MOBA/FPS 品类
- 完善 Web 端、通用 OCR、AI 规则辅助
- 上线 C 端全品类工具，开启云端存储付费

### 阶段 4：生态建设（2~4 个月）

- 通用计算内核拆分为独立仓库
- 正式推行商业授权
- 社区共建配置库（玩家提交适配配置，免费高级权益激励）

## 10. 社区分享平台（插件工坊 / Calc Hub）

用户需求：GUI 界面、计算逻辑、OCR 配置、游戏数据包全部可以在一个网站上分享。

### 10.1 核心理念

可以理解为**游戏数值工具的创意工坊 / 插件市场**：

| 层次 | 说明 |
|------|------|
| 底层不动 | 通用抽象计算框架（核心引擎，GPL 开源） |
| 上层全开放 | GUI 主题、计算公式包、OCR 规则、游戏数据包，全部在网站上共享 |

任何人都能上传、下载、一键使用，不用改代码。

### 10.2 合规性（GPL 协议下绝对安全）

✅ **完全合规，不触发 GPL 传染，是开源社区标准玩法。**

| 组件 | 协议 | 说明 |
|------|------|------|
| 核心框架 | GPL | 开源，受协议保护 |
| GUI 主题 / 计算配置 / OCR 规则 | 独立资源文件 | 不是框架的衍生代码，只是数据/模板/配置 |
| 玩家分享的插件 | 自由许可证 | 作者允许社区自由分享、修改、传播 |
| 商用插件 / 二次开发 | 商业授权 | 走双授权体系 |

**对标全世界开源项目的标准做法**：VSCode 插件市场、Chrome 扩展、Steam 创意工坊 — 底层 GPL，上层插件自由分享。

### 10.3 技术实现（极低成本）

**不需要服务器、不需要数据库、不需要复杂后端，纯静态网站就能跑。**

| 组件 | 方案 | 成本 |
|------|------|------|
| 统一插件格式 | JSON Schema（gui-theme.json / game-calc.json / ocr-rule.json） | AI 一键生成 |
| 分享网站 | Vercel / GitHub Pages 免费部署 | 0 元 |
| 工具内置导入 | Web 版 / 客户端直接读取插件文件，自动加载 | 已有 ComputeSheet 基础 |
| 社区维护 | 插件上传到 GitHub，玩家 PR，作者审核 | 社区驱动 |
| **总开发时间** | AI 辅助 **1~2 天** | 极低 |

### 10.4 网站功能规划

| 功能 | 说明 |
|------|------|
| 浏览 GUI 主题 | 预览图 + 一键下载 / 一键导入 |
| 下载游戏计算包 | 各游戏适配包市场 |
| 一键导入工具 | 客户端直读插件文件 |
| 玩家上传分享 | 上传评分系统 |
| 质量保障 | 评分、标签、官方认证、版本校验 |

### 10.5 价值分析（生态级升维）

这个设计不是一个小功能，而是**生态级别的设计**，直接改变项目命运：

| 维度 | 之前 | 加上插件平台后 |
|------|------|--------------|
| 作者工作量 | 必须自己维护所有游戏逻辑和界面 | 社区自发上传/维护，释放 90% 工作量 |
| 用户体验 | 单一界面、固定游戏 | 想用什么界面下载什么主题，想玩什么游戏下载什么包 |
| 项目壁垒 | 工具，容易被复制 | **生态**，插件越多/用户越多/生态越牢 |
| GitHub Star | 6k~12k（通用框架） | **10k~20k+**（生态型项目） |

**对标项目**：VSCode、Docker、Homebrew — 这类生态型开源项目的共同特征是底层开源 + 上层插件市场。

### 10.6 与作者理念的完美契合

| 作者坚持 | 兼容性 |

| 开源、社区共享 | ✅ 开源精神的极致体现 |

## 11. 风险与缓解

| 风险 | 概率 | 缓解方案 |
|------|------|---------|
| 规则复杂度爆炸 | 中 | 坚持插件化 + 配置化，内核只做基础能力 |
| UI 适配压力 | 中 | 配置驱动动态 UI，不硬写页面 |
| 数据维护量 | 中 | 社区共建，用「免费高级权益」激励 |
| 合规范围扩大 | 低 | 纯本地计算、不读内存、不抓包、不做外挂 |
| 开发周期过长 | 低 | AI 辅助编码，渐进式迭代，不一次做完 |

## 12. 总结

这一步深度抽象，是整个项目「升维」的关键：

1. **技术上**：从一款手游工具 → 一套通用游戏战斗数值底层框架
2. **市场上**：从二游玩家 → 全品类玩家 + 游戏从业者（B 端高价值）
3. **商业上**：从单一赞助 → C端服务 + B端授权 + 订阅 + API 多元收入
4. **影响力上**：从 3k~8k Star 的垂直工具 → 20k~35k 的圈内标杆项目
