# 仓库历史清理评估

> 结论：**不重写历史**。历史中的构建产物与模型权重保留，当前与新增提交由大文件钩子与布局/许可门禁约束。
> 本文件记录只读扫描结果与决定，供协作者复核；扫描工具不会执行任何写操作。

## 1. 扫描方法

```powershell
python tools/quality/supply_chain/scan_git_history.py
python tools/quality/supply_chain/scan_git_history.py --json-out history-report.json
```

工具实现：[`tools/quality/supply_chain/scan_git_history.py`](../tools/quality/supply_chain/scan_git_history.py)

- 对象枚举：`git rev-list --objects --all`（全部分支与标签可达对象）
- 类型/大小：`git cat-file --batch-check=%(objectname) %(objecttype) %(objectsize)`
- 大文件阈值：4 MiB（与 `.pre-commit-config.yaml` 的新增大文件上限一致）
- 可疑模式：`dist/`、`build/`、`node_modules/`、`target/`、`__pycache__/`、`.pyz`、`.pyc`、`.exe`、`.dll`、`.so`、`.dylib`、`.whl`、`.7z`、`.zip`、`.tar.gz`
- 工具只读：不调用 `filter-repo`、`filter-branch`、`gc` 或任何删除/重写命令

## 3. 决定与理由

**决定：不重写 Git 历史。**

理由：

1. 三个对象均**不在当前提交**中，不影响新 clone 的工作区正确性；
2. 历史重写会改变全部提交哈希，破坏现有标签、发布记录、协作者本地分支与 Issue/PR 引用；
3. 仓库体积仍在可接受范围，清理收益低于协作成本；
4. 本项目为单维护者模式，重写窗口的安全收益有限，风险主要是不可逆的历史丢失。

**接受的风险**：

- clone 仍需下载历史对象，体积偏大；
- 审计工具扫描历史时会出现已知噪音。

该风险已登记在 [`docs/开放问题与治理.md`](开放问题与治理.md) 的 R-22（状态 `accepted`），复审日期 2027-05-04。

## 4. 防止新增

- `.pre-commit-config.yaml` 的 `check-added-large-files` 上限 4096 KB，新增大文件在提交前失败。
- `.gitignore` 覆盖构建产物、模型权重、临时目录与虚拟环境。
- 布局门禁跳过 `dist/`、`build/`、`target/` 等产物目录，避免把生成物当源码统计。
- 发布流程只从受控构建脚本产出制品，不把 `dist/` 提交回仓库。

## 5. 未来若需清理

如仓库体积成为实际阻塞，按以下顺序单独处理，不与普通修复混提：

1. 确认对象无保留价值，并通知所有协作者；
2. 在镜像仓库演练 `git filter-repo`，核对标签与提交映射；
3. 选择低活跃窗口执行，强制推送所有分支与标签；
4. 更新发布记录与协作者本地 clone 指引；
5. 重新运行本扫描并归档报告。
